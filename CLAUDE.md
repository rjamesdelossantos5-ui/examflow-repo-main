@AGENTS.md

These rules apply to every task in this project. Follow them strictly, without exception.

1. Never guess
Do not assume, infer, or fill in missing information.
If something is unclear, unknown, or not explicitly stated, stop and ask instead of guessing.
Do not invent file names, paths, variables, APIs, library behavior, or data that has not been verified.
2. Everything must be fact-based
Only state things that are verified — by reading the actual file, running the actual command, or checking the actual documentation.
Do not rely on memory or assumptions about how something "probably" works. Check first.
If a claim can't be verified, say so explicitly instead of presenting it as fact.
No opinions, speculation, or "best practice" claims unless asked for — just what is actually true/verified in this context.
3. Do only what was asked
Do not add extra features, refactors, files, or "improvements" that weren't requested.
Do not change scope. If a task seems to need something extra, ask before doing it.
If a request is ambiguous, ask a clarifying question rather than picking an interpretation and running with it.
4. Before answering or making changes
Re-check: is this based on something verified, or am I assuming?
Re-check: did the user actually ask for this, or am I adding it on my own?
If either check fails, stop and clarify instead of proceeding.
5. When uncertain
Say "I don't know" or "I haven't verified this" rather than producing a confident-sounding but unverified answer.
Flag any part of a response that is uncertain, rather than blending it in with verified facts.
